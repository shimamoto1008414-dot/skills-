# Dual-Model Executor / Advisor

実行役(Executor)と相談役(Advisor)の 2 モデル体制で開発タスクを進めるスキル。
普段は速くて安い実行役が手を動かし、**難所だけ**上位モデルの相談役に助言を求める。
相談の書き方の型と回答の検証手順は `references/consultation-template.md` に分離して
あるので、実際に相談するときだけ読み込むこと(トークン節約のため)。

## 1. 役割分担

| 役割 | モデル | 担当 |
|---|---|---|
| 実行役 (Executor) | 現在のセッションのモデル(例: Sonnet) | 実装・調査・テスト・コミットなど作業全般 |
| 相談役 (Advisor) | **相談のたびにユーザーが選ぶ**(§3 参照) | 行き詰まりの打開・設計判断・リスク評価への**助言のみ** |

- 相談役は助言のみ。**ファイルの変更・コミット・外部への操作は必ず実行役が行う。**
- 相談役のモデルは固定しない。相談が発生するたびに AskUserQuestion でユーザーに
  選んでもらう。ただしユーザーが「以後の相談は◯◯で」と明示したら、そのタスク中は
  聞かずにそのモデルを使ってよい。
- このスキルが有効なあいだも、作業の進め方・報告の仕方は普段どおり。変わるのは
  「詰まったときの逃げ道が、闇雲な試行錯誤ではなく相談役への相談になる」ことだけ。

## 2. 相談するタイミング(トリガー)

次のいずれかに該当したときだけ相談する:

1. **行き詰まり** — 同じ問題に対する修正を 2 回試して 2 回とも失敗した
   (エラーが変わらない・悪化した・原因の仮説が尽きた)。
2. **設計・アーキテクチャ判断** — 後から変更しにくい構造の選択(データモデル、
   API 設計、ライブラリ/依存の追加など)で、複数案から確信を持って選べない。
3. **影響範囲の大きい変更** — 多数のファイルに波及するリファクタや、既存の挙動を
   壊しうる変更の進め方に迷う。
4. **セキュリティ・データ破壊のリスク** — 認証・権限・暗号・破壊的マイグレーション
   など、間違えたときの被害が大きい設計。
5. **セカンドオピニオン** — 一区切りついた成果物のレビューをユーザーが求めたとき。

### 相談しないこと(実行役が自力でやる)

- コード・ドキュメント・Web を調べればわかること(まず Read / Grep / WebSearch)。
- 構文エラー・typo・単純なバグの 1〜2 回目の修正試行。
- **ユーザーの好み・要件の確認** — これは相談役ではなくユーザー本人に
  AskUserQuestion で聞く。相談役はユーザーの代わりにはならない。
- 相談役への再質問の繰り返し。1 トピックにつき原則 1 往復。追加で聞きたいことは
  次の相談にまとめる。

## 3. 相談のやり方

### 3-1. まず相談役モデルをユーザーに選んでもらう

相談トリガーに該当したら、**相談を実行する前に毎回** AskUserQuestion で
相談役モデルをユーザーに選んでもらう。質問には「何を相談したいか」を一言で
含めること(ユーザーが相談内容の重さに応じてモデルを選べるように)。

```
AskUserQuestion(
  questions: [{
    question: "◯◯(相談したい内容の要約)について相談役に相談します。どのモデルに相談しますか?",
    header: "相談役",
    options: [
      { label: "Opus(推奨)", description: "上位モデル。設計判断・難しいデバッグ向け。コスト高" },
      { label: "Sonnet",      description: "バランス型。標準的な相談・レビュー向け" },
      { label: "Haiku",       description: "軽量・高速。簡単な確認向け。コスト低" },
      { label: "相談しない",   description: "相談をやめて自力で続行する" }
    ],
    multiSelect: false
  }]
)
```

- 「相談しない」が選ばれたら相談は中止し、自力で続行する(必要なら方針を
  ユーザーに直接聞く)。
- 選択肢の推奨は相談内容に合わせて変えてよい(軽い確認なら Haiku を推奨にする等)。

### 3-2. 選ばれたモデルで相談役を起動する

Agent ツールで相談役サブエージェントを**同期実行**する
(回答を待ってから作業を続けるので `run_in_background: false`)。

- 設計・進め方の相談 → `subagent_type: "Plan"`(読み取り専用でコードを調べて計画・推奨案を返す)
- デバッグ・原因分析・成果物レビュー → `subagent_type: "general-purpose"`
  (プロンプト内で「ファイルは変更しない。分析と回答のみ」と明示する)

呼び出し例:

```
Agent(
  subagent_type: "Plan",            // デバッグ相談なら "general-purpose"
  model: "opus",                    // ← 3-1 でユーザーが選んだモデル
  run_in_background: false,
  description: "設計判断を相談",
  prompt: <references/consultation-template.md の型で組み立てた相談文>
)
```

**相談役は毎回まっさらな状態で起動する**(この会話の文脈を一切知らない)。
ゴール・制約・試行錯誤の履歴・関連ファイルのパスをすべて相談文に含めること。
相談文の型と回答の検証チェックリストは `references/consultation-template.md` を
読んでから書く。

環境の都合で Agent ツールの model 指定が使えない場合のフォールバック:
Bash で `claude -p --model <選ばれたモデル> "<相談文>"` を実行する(ヘッドレス呼び出し)。

## 4. 回答の扱い方

1. **助言であって命令ではない。** 回答をそのまま適用せず、コードベースの実態と
   照合して検証する(参照されたファイル・API が実在するか、前提が合っているか)。
2. 検証して妥当なら採用して作業を続行する。採用した判断と理由は最終報告に
   1〜2 行で残す(「◯◯で詰まり、相談役の推す案 B を検証のうえ採用」など)。
3. 回答がユーザーの明示的な指示と矛盾する場合は**ユーザーの指示が優先**。
   矛盾が重大(指示どおりだと壊れる等)なら AskUserQuestion でユーザーに確認する。
4. 回答が的外れ・検証で誤りと判明したら、その事実を踏まえて自力で続行するか、
   論点を絞ってもう 1 回だけ相談し直す。それでも解決しなければユーザーに現状を
   報告して指示を仰ぐ(黙って同じ相談を繰り返さない)。

## 5. コスト規律

- 相談役の起動は高コスト(上位モデル+コンテキストの再説明)。**1 回の相談に
  関連する質問をまとめる。**
- 1 つのタスクでの相談は目安 3 回まで。超えそうなら、タスクが大きすぎる・
  前提が崩れているサインなのでユーザーに相談する。
- 相談文に引用するコードは判断に必須の断片だけにし、残りは
  `パス:行番号` で示す(相談役サブエージェントは自分でファイルを読める)。

## 6. 作業の流れ(まとめ)

1. 通常どおり実行役として作業する。
2. §2 のトリガーに該当したら、AskUserQuestion で相談役モデルをユーザーに
   選んでもらう(§3-1。毎回聞く)。
3. `references/consultation-template.md` を読み、相談文を組み立てて
   選ばれたモデルで相談役を同期起動する。
4. 回答を検証し、採用/不採用を決めて作業を続行する。
5. 最終報告に「どこで何を(どのモデルに)相談し、どう判断したか」を簡潔に含める。
