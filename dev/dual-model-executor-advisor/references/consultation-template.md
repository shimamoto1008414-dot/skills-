# 相談文の型(Consultation Template)

相談役は**この会話を一切知らない**前提で書く。以下の型をそのまま使い、
不要なセクションだけ削る。

```
## 状況
- リポジトリ / 対象: <パスと、何を作っている・直しているか>
- ゴール: <このタスクで達成したいこと>
- 制約: <ユーザーの指示・技術的制約・互換性要件など>

## これまでの試行(行き詰まり相談の場合のみ)
1. <試したこと> → <結果。エラー出力は要点のみ引用>
2. <試したこと> → <結果>
- 現時点の仮説: <あれば>

## 関連ファイル
- path/to/file.py:120-160 — <そこに何があるか一言>
- path/to/other.ts — <一言>
(あなたはこのリポジトリのファイルを直接読める。コード断片の引用は判断に
必須の箇所だけに絞ってある)

## 質問
<1 つに絞った具体的な質問。可能なら選択肢を並べて比較を求める>
- 案A: <内容と自分が見ているメリット/デメリット>
- 案B: <同上>

## 回答してほしい形式
- 推奨案とその理由(トレードオフを含めて)
- こちらが見落としているリスク・確認すべき点があれば指摘
- ファイルの変更・コミット・コマンドによる状態変更はしないこと。分析と回答のみ。
```

## 良い相談・悪い相談

**悪い例:**
> テストが落ちます。どうすればいいですか?

文脈ゼロ・質問が漠然としていて、相談役は一般論しか返せない。起動コストが無駄になる。

**良い例:**
> (上の型に沿って)ゴールと制約、試行 2 回分の内容と結果、エラーの要点、
> 関連ファイルのパス、そして「案A と案B のどちらを推すか、理由と併せて」という
> 絞った質問が入っている。

ポイント:
- **質問を先に決めてから相談文を書く。** 質問が決まらないなら、まだ相談の段階では
  ない(自分の調査が足りていない)。
- 選択肢を出せるところまで自分で考えてから聞くと、回答の質が大きく上がる。
- 複数の論点があるなら 1 回の相談にまとめ、質問を番号付きで並べる。

## 回答の検証チェックリスト

回答を採用する前に必ず確認する:

- [ ] 回答が参照するファイル・関数・API は実在するか(Read / Grep で確認)
- [ ] 回答の前提(バージョン・設定・環境)は今のリポジトリと一致するか
- [ ] ユーザーの明示的な指示と矛盾していないか(矛盾するならユーザー優先)
- [ ] 変更を小さく切り出して試せるか(試せるならまず小さく検証してから全体に適用)

1 つでも引っかかったら、そのまま適用しない。実態に合わせて修正して使うか、
不採用として自力の方針に戻る。
